# Regional simulation handoff

The live launcher still runs one authority per planet over continuous planar geography. The coordinator now supports configured geographic authorities and durable crew transfers, in addition to the simulation codec. Worker orchestration, browser socket switching and border combat remain incomplete; this is not a claim of live cross-region gameplay or measured population capacity.

## Implemented

`shared/entity-id.ts` accepts checked safe-integer IDs. Durable characters retain low 31-bit IDs, and coordinated workers reserve batches above the old 32-bit space before constructing their simulation. Protocol 23 uses canonical 1–8 byte varints for every entity reference, including roster/chat, combat events, seated hull references and construction messages. A new dynamic ID initially occupies five bytes; small human IDs occupy fewer. Sequences remain unsigned 32-bit counters. All clients and workers must update together.

`EntityLedger` durably reserves never-reissued ranges of 65,536 IDs, stored as one issuance row per batch. A worker starts with eight blocks and prefetches another batch when at most two blocks remain. Gameplay, bots, vehicles, projectiles, pickups and wildlife share the same synchronous pool. There is no per-shot coordinator write and no allocator wrap; reservation exhaustion stops the worker. The database counter advances atomically with issuance, and startup also checks the issuance high-water mark. Reservations, including unused ranges from failed startups, are never reclaimed.

A bootstrap request binds a fresh process ID to its planet/region. An identical lost-response retry is permitted only before that process registers. Registered or retired process IDs cannot bootstrap again; the launcher supplies a fresh UUID for every restart. Subsequent reservation retries require the same request parameters and current authority epoch, even when returning a cached receipt. Prefetch retries transient failures with the same request ID while consuming buffered IDs. Hull transfer checks initial provenance against the issuance ledger and subsequent provenance against committed ownership. Legacy namespaces remain available for standalone/compatibility tests; they are not the coordinated worker allocation path.

The restart regression migrates a real aircraft crew and its live bombs, replaces the original source process, spawns new hulls/bots/projectiles/wildlife, and brings the crew back into the replacement alongside its local objects. Their IDs remain distinct and the actual snapshot preserves the returned hull reference. Separate checks cover lost HTTP replies, cold coordinator recovery, the final safe-integer block, malformed varints, stale reservation tokens and buffer exhaustion. These establish identity behavior, not distributed population capacity.

Planetary clocks and geographic authority leases persist in SQLite. The clock reserves every granted worker's future simulation horizon; coordinator restart advances past it and conservatively fences replacement ownership for a full lease period. Cold workers initialize at shared planetary time. Live workers retain bounded catch-up debt and fail/restart beyond five seconds rather than skipping physics. Clock ticks are checked 64-bit values on the browser wire; heartbeat sampling reports its round-trip uncertainty. Registration epochs and a character's saved world incarnation fence retired workers' writes. The directory keys authority by `(planet, region)`, while the current launcher registers only region `world` for each planet.

The clock recovery test uses a real worker and connected character, restarts the SQLite coordinator, verifies orderly failure on excessive debt, then admits the same character to a new worker at persistent planetary time. The three-process crash test and camp response-loss recovery also exercise this scheduler. This does not test a regional border or an atomic crew ownership commit.

`Game.takeHandoff(ids)` captures and detaches a group synchronously between simulation ticks. Starting from a passenger includes the pilot and the shared hull. The operation validates group consistency and the serialized size before deleting any map entries. It retains original player objects for local rollback and produces a JSON record containing no connection/sink objects.

The record contains all current `ServerPlayer` fields except the sink, with Sets represented as arrays; movement and aircraft attitude; ammunition, reloads and cooldowns; input sequence/queue state; allegiance and exploration progress; hulls and their motion state; owned projectiles with guidance/fuse state; and the recent lag-compensation poses for the transferred actors. A null fuse explicitly represents impact/range-limited projectiles whose runtime fuse is Infinity. Non-finite pose/state values are rejected. The maximum record is 1 MB, with 64 actors/hulls, 2,048 projectiles and the normal history window.

`Game.acceptHandoff(record, sinks)` requires the same planet and a destination clock no more than five seconds ahead of the source. It validates the whole record before installing actors and rejects occupied IDs. Actor timers pause for the transfer interval, while moving-platform timestamps remain in the planetary time domain. Ordinary physics then carries train/lift passengers to the platform's current position. A new sink is required for every human actor. This method does not establish ownership: the caller must first obtain the coordinator's commit.

`Game.restoreHandoff(detached)` preserves original local player/connection objects. It is used when a planetary launch fails and the source lease can still be proved. It restores pending explosives and movement instead of treating the rollback as a fresh arrival. A rollback that cannot be validated falls back to normal character reconnect/recovery. Successful interplanetary journeys continue to restore persistent profiles at the destination spaceport, as intended.

Tests exercise unsigned IDs throughout the wire protocol, migration/restart, identity across a real gateway launch/reconnect, next-tick simulation after JSON transfer, jumping/reloading, a two-seat aircraft and its projectile, and rejected/duplicate imports. These checks validate primitives and local rollback, not a distributed regional battle.

## Durable geography and crew ownership

`RegionGrid` defines an immutable, versioned rectilinear layout over the existing surface. Ordered cuts cover the entire planetary envelope without overlap. Internal seams have half-open ownership, exact border positions have one owner, and overshoot outside the physical boundary retains an owner. Cells are at least 128 metres wide, with at most 64 by 64 cells per layout. This is geographic partition metadata, not spherical terrain or proof that that many workers can run.

The coordinator persists layouts and migrates the old whole-planet authority table without resetting its fencing epochs. Every worker registration names a region in the installed layout; workers cannot invent overlapping bounds. Independent region leases share the planetary clock. Coordinate lookup uses binary searches followed by a keyed authority lookup. Reconnect routing follows saved position, while fresh characters and orbital arrivals use the configured entry region. A missing region stays unavailable instead of routing a character to a different place. Planet capacity and population aggregate live regions; admission and pending-arrival capacity remain local to the destination region.

Layout changes require a newer version and expiration of every planetary world and character lease. The transaction remaps saved characters, advances their epochs, aborts unresolved preparations and clears the transient hull-ownership registry for the cold layout restart. Exact layout retries are idempotent while the world is running. The current launcher does not yet deploy partitioned layouts; these private control-plane operations are for the upcoming region host integration.

`RegionTransfers` implements this protocol behind authenticated private HTTP endpoints:

1. The source freezes the entire crew and obtains `Game.takeHandoff`. `prepareRegional` validates the same planet/layout, both authority epochs, every character lease, complete human membership, destination coordinates and hull ownership. It reserves enough destination capacity for the whole group and persists the validated runtime record. Bot-controller migration is explicitly rejected until its missing state is supported. Camp spending is reconciled into the staged record and recovery profiles.
2. While preparation is unresolved, old checkpoints, releases, abandoned handshakes, camp actions and competing transfers cannot change those characters. A preparation lasts at most five seconds. The source must keep the original detached objects for rollback and must not continue simulating them.
3. The destination reads the record, checks `prepareArrival` against its real simulation and prospective sinks, then acknowledges the payload hash and its clock. Reading the payload alone does not authorize commit or simulation.
4. `commitRegional` atomically changes every character's lease/holder/region and every carried hull's durable owner. It requires the exact source, staged hash, destination readiness, still-live authorities and unchanged character ownership. The destination obtains a receipt and may import only while those committed leases and the runtime clock window are still valid. Full simulation state is separate from the smaller crash-recovery profile.
5. A retry returns the same decision and fixed lease times. A late abort cannot undo a committed transfer. An aborted preparation can be rolled back only while source ownership remains valid; otherwise ordinary reconnect/recovery must resolve it. Coordinator restart aborts uncommitted readiness but preserves committed outcomes. Its clock recovery gap prevents importing an old runtime record as if no time passed.

Full runtime payloads become eligible for removal after one minute; small outcomes remain for one day of retries. Cleanup runs during preparation and has indexed expiry/transfer lookups. Old ownership epochs still fence replay after an outcome is pruned. The private HTTP limit is 2 MB to fit the existing 1 MB runtime envelope plus ownership metadata. This does not measure coordinator throughput or high availability.

The new tests use two real `Game` simulations and private coordinator HTTP. A shared movement tick crosses a geographic seam; a proxy deliberately drops a successful commit response; retry and import retain velocity, jump/reload state and queued input. Aircraft tests transfer pilot, passenger, hull, attitude and a live projectile as one unit, return the same crew, and reject partial membership, stale epochs, capacity overbooking and changed hashes. Other cases cover cancellation, expired preparations, destination replacement, legacy database migration and coordinator restart. They do not exercise automatic worker or browser handoff.

## Persistent regional camps

Camp reads derive their bounds from the authenticated authority's registered planet, region and layout. They include a 384 m neighbor margin for nearby rendering and shared wall collision. An indexed position query replaces whole-planet loading for configured geographic workers. A durable revision per 128 m cell includes removals, so packing the final module still changes a previously populated view. Cursors bind the authority epoch and layout; unchanged views avoid sending geometry again. The ledger migrates legacy positions and revisions inside one transaction, in 512-row pages supported by Node 22.11, without changing site JSON, IDs or spending.

Writes require current character/world ownership and the module location's region. Readable neighboring modules cannot be independently mutated by the observer. Each construction transaction returns the complete current cell, at most four modules, alongside the idempotent payment receipt. The worker overlays newer committed cells onto delayed regional snapshots. This prevents both erasing a new wall and resurrecting a module built and packed before that receipt, while allowing freshness to advance during continuous construction. Retrying an older operation can return its original operation revision with a newer complete cell. Unchanged local camp stamps survive distant changes.

`WorldNode` refreshes its camp view during the two-second heartbeat. A view must be renewed within about seven seconds for readiness and simulation to continue. An uncertain construction outcome also pauses simulation until a subsequent synchronization succeeds; a reply started before that uncertainty cannot clear the pause. A lost view endpoint therefore cannot leave the worker indefinitely ready against stale walls merely because authority renewal succeeds.

Tests cover edge/corner views, one mutation owner, two real collision fields, two `WorldNode` instances refreshing over private HTTP, view expiry/recovery while authority stays live, delayed cell receipts and populated legacy migration including 1,202 active/packed records. Desktop and touch browser checks pass construction, spending, collision, services, packing and reload, with desktop worker replacement. These establish scoped persistence and asynchronous replication. They do not establish a synchronized border battle or browser handoff.

## Integration still required

1. Implement lazy geographic worker startup and region-scoped static spawns, pickups, territory and wildlife. Camp loading is now scoped and `WorldNode` accepts a region, but the launcher still registers `world` and other controllers still assume a full planet. A home machine must not eagerly simulate every region. Do not configure a partitioned live planet and expect the current launcher to serve it.
2. Connect source and destination orchestration to the durable protocol: freeze every crew connection between ticks, stage against the real destination simulation, preserve original rollback objects, install committed sinks and resolve interruption/replacement outcomes. Existing actor/lease identity guards prevent delayed callbacks from deleting a returned actor or cancelling its new launch; preserve those guards in the orchestration. Keep the public browser socket and streamed terrain while switching private upstreams; preserve input sequences without issuing a fresh world welcome.
3. Replicate neighboring actors as read-only representations and route damage, guided projectiles, explosions and attribution to their actual owner with deduplication and epoch checks. A border must not separate players who can see or shoot each other.
4. Transfer Bot controller state as well as Game-owned state, partition transport-linked hull ownership and respawn lifecycles, and validate train/lift/ferry riders at borders. The codec alone does not transfer a vehicle spawn site's lifecycle or the wildlife/loot controller.
5. Test complete physical routes and browser continuity on foot, in every hull class, on moving trains/ferries and during combat. Include source/destination/coordinator failures and dense-border load, then measure distributed concurrency and coordinator throughput/availability.

Camp refresh is currently asynchronous: neighbors can observe a changed wall up to a heartbeat later. Before enabling regional combat, coordinate collision activation/removal at shared simulation time and route building across a seam to the geographic owner. The current owner fence deliberately rejects that construction location instead of providing this routing. Preserve spending watermarks through runtime and durable handoff; the staging protocol already reconciles them before committing. The single coordinator, current module budgets and regional read queries still need realistic distributed load measurements.
